# 第五阶段：串行会话与事件终端

## 使用方式

在项目目录打开聊天；等待输入时，后台每秒扫描既有 `automations.pending_events`，无需输入消息触发消费：

```powershell
python -m agent.main --root memory
```

检查器仍独立运行，负责定时检查、邮件 UID 增量同步和入队，不调用 Agent：

```powershell
python -m agent.automation_checker --interval 10
python -m agent.automation_checker --once
```

自动事件在 Windows 新控制台运行 `python -m agent.main --event ...`。这个入口由消费者自动启动，不需要手动填写内部认领参数。每个事件有独立 `FileTools`、会话 ID、消息历史和邮件草稿引用。子进程启动后立即取得事件生存期锁，即使正在等待 API token，也不会被重复启动。

消费者只在聊天进程存活时运行；退出所有聊天后，已经打开的事件终端继续工作，尚未处理的事件在下次聊天启动后恢复消费。本阶段没有登录自启动、图形界面或并行模型调用。检查器不会自行启动聊天程序。

## 直接命令

命令直接由程序处理，不经过模型：

| 命令 | 作用 |
| --- | --- |
| `/scheduler` | 当前执行会话、进程、Memory 事务归属、已提交用户输入 |
| `/automation active` | 活动/暂停/失败事件、会话、PID、生存期锁、阶段、下次重试时间及错误 |
| `/results` | 最近 20 个结果，包含完整回复 |
| `/results <事件ID>` | 指定事件完整结果 |
| `/commit` | 展示当前事务 diff，明确输入 `yes` 才提交 |
| `/cancel` | 取消当前会话拥有的 Memory 事务 |
| `/exit` | 退出当前会话并取消未提交事务 |
| `/event end` | 在事件反馈提示处结束事件，等同事件终端的 `/exit` |
| `/automation event-resume <事件ID>` | 恢复用户主动结束的事件；所属规则也必须处于 active |
| `/automation auto pause` | 暂停启动新的自动事件，跨终端、重启后保持 |
| `/automation auto resume` | 恢复自动消费 |
| `/automation consume` | 使用独立事件会话手动消费，在当前终端展示完整结果，不关闭聊天终端 |
| `/automation check`、`pending [规则编号]` | 保留原有检查、待处理事件查看 |
| `/automation list/get/create/update/pause/resume/cancel` | 保留前四阶段规则管理 |

自动暂停不终止正在执行的轮次或等待用户的事件，也不阻止已有最终 reply 的结果保存和投递。手动消费不受自动暂停控制，用户再次明确执行 consume 可以立即重试；后台失败重试从 30/60 秒起退避，最长一小时。当前聊天自己持有事务时，手动消费会提示先提交或取消，避免当前终端等待自身释放锁。

## 两层锁与恢复

所有 `run_turn()`、独立邮件草稿及导入调用都经过仓库 `data/runtime/execution.lock`。Windows 使用 `msvcrt` 字节锁，其他平台使用 `flock`；进程退出由操作系统释放。嵌套邮件 Agent 共用外层轮次，不重复排队。轮次锁覆盖模型请求、工具执行以及工具内部确认，普通输入提示不持有轮次锁。已提交的用户输入有 OS 锁保护的排队凭据，优先于尚未进入执行的自动轮次，不抢占已开始的轮次。

首次 Memory 修改取得该 Memory 根目录的 `.memory-owner.lock`，记录会话和 PID，再从正式 Memory 初始化 `.memory-temporary/`。这个锁跨轮次保留；write/edit/delete 和 `pending/` 使用同一事务。只读会话读取正式 Memory，所属会话读取 Temporary。启动新会话不会清理有效持有者的 Temporary。恢复轮次前会重新执行历史中的 Memory 检索，避免继续使用其他会话提交前的旧工具结果。

锁顺序是轮次锁 → Memory 所有权锁 → 短期事务元数据锁；不需要模型的恢复/事务操作从所有权锁开始。等待其他所有者时先释放轮次锁，再重试，输出持有者和等待原因。用户输入优先并不覆盖 Memory 事务独占权。

`yes` 且保存成功才释放事务；`no` 保留修改和锁。`cancel`、正常退出丢弃修改；其他会话的 cancel 不能取消持有者。提交先备份正式树并写恢复标记，失败时回滚、保留候选；提交中进程崩溃，下次安全取得所有权锁后先恢复正式树，再丢弃失效候选。不得手工删除仍被使用的锁文件。

窗口关闭事件尽力记录为用户暂停；强制结束进程、崩溃或未收到关闭回调按失败退避处理。无论哪种退出，失效 Temporary 都不会合并。控制台关闭回调只更新事件暂停字段，不与 Agent 线程并发修改 Memory。

## 事件生命周期与结果

继续使用原表和 pending 事件；增加活动会话、PID、启动时间、反馈阶段、暂停标记、消息历史等 JSON 字段，不新增任务表。消费者短暂持有现有 consumer 锁认领，随后释放；实际执行锁由事件进程获取。活动事件另有 OS 生存期锁；进程在，反馈等待多久都不会重开。父进程跟踪退出状态；父进程重启后通过生存期锁及 60 秒启动宽限恢复失效认领。

事件任务通过普通 `run_turn()` 和原工具运行。Memory 合并、邮件发送依旧执行 Runtime 确认；不会默认批准。中间回复转入反馈提示并提交“需要用户处理”通知。事件专用 `complete_event(reply=...)` 工具标记明确完成，且程序拒绝在仍有 Memory 事务或与其他工具同批调用时完成。普通聊天、嵌套邮件处理和只读草稿不提供这个工具。

完成顺序：保存最终 reply 到 pending_events → 原子保存完整结果 → 向 Windows 提交通知 → 移除事件并在同一数据库更新中完成一次性规则 → 子进程退出。通知或文件失败保留 reply，之后只重试投递，不重跑模型。手动消费以终端展示成功代替通知接受。规则被暂停时保留最终 reply，恢复规则后投递。

结果固定保存在 `data/results/<事件ID的SHA256>.json`，包含事件 ID、规则 ID/名称、发生和完成时间、完整回复。相同事件复用同一个文件。`data/results/`、`data/runtime/`、Memory 锁/备份/恢复标记都排除 Git。Windows 通知通过 PowerShell WinRT 提交，使用当前用户 `Software\Classes\AppUserModelId\PersonalAIHelper` 的显示名称注册，不设置自启动。通知失败不影响终端确认交互。

通知 API 接受仅表示系统接受提交，不表示用户已看到或阅读；免打扰、通知设置、企业策略可能影响显示。

## 验证及已知边界

运行回归：

```powershell
python -m unittest discover -s tests -q
python -m unittest discover -s tests -p test_phase5.py -v
```

测试覆盖真实 Windows 子进程互斥、用户优先、跨会话只读隔离、拒绝提交保锁、取消释放、强制终止后的恢复、提交部分失败回滚和提交中崩溃恢复；离线事件测试覆盖空闲后台消费、独立终端启动参数、反馈保活、用户退出/恢复、失败退避、完整结果、通知失败后不重跑模型、原有手动消费和邮件 UID 增量同步。

本次完整回归 217 项通过，其中第五阶段专项 20 项；其余包括前四阶段和 UID 增量同步测试。

Windows 通知 API 已实际提交一次中文测试通知并正常返回；这不验证横幅可见性或通知中心留存。独立终端窗口创建、中文输入交互、点击关闭按钮及关闭回调、通知实际呈现仍需人工端到端验收；这些项目不能用 mocked Popen/notify 测试代替。

保留的边界：通知成功后、清除事件前崩溃可能重复通知；工具执行后、最终 reply 保存前中断可能重复执行工具；不提供工具副作用严格去重。多个仓库副本不共享执行锁，多个 Memory 根各自拥有事务锁；同一项目的多个终端共享全局轮次锁。
